## 一、边界说明：能统计什么、不能统计什么

**能统计**：每次模型调用的 `input_tokens` / `output_tokens` / `cache_read_input_tokens`，全部记录在会话 transcript（JSONL）里。

**不能统计**：**积分余额与实际扣费**。积分属于平台账户层数据，沙箱内没有任何接口、环境变量或缓存文件暴露它。因此本报告只能给出 **token 用量**，不能给出"花了多少积分"。

若要知道积分，只有两条路：
1. 在 App / 网页端的账户页查余额与消费记录；
2. 用本报告的 token 数 × 你套餐的单价自行换算（单价随套餐与缓存折扣变化，本仓库不硬编码）。

### 两个反直觉的观察

1. **第 1–100 次就已经是 10 万级**，不是"从几千慢慢涨上来"。原因是这个会话承接自一次 **compact 压缩**——开场即带着摘要 + 恢复的历史，起点就很高。
2. **曲线不是单调上升，而是锯齿状**。第 301–400 次冲到 14 万后回落，末期降到 7.5 万。这说明**平台的自动压缩在起作用**：撞到上限就把早期内容压成摘要，窗口回落。所以长会话不会被"无限拖慢"，但会稳定在 **7–14 万**这个区间反复震荡。

换句话说：**成本不会无限增长，但会长期停在 10 万/次这一档**。773 次调用 ≈ 7800 万 input，就是这么累加出来的。

## 四、可复用的采集方法

```bash
# 当前最近一个会话
python3 scripts/usage_stats.py

# 逐轮趋势（最直观）
python3 scripts/usage_stats.py --trend 20

# 所有会话横向对比
python3 scripts/usage_stats.py --all
```

脚本细节：
- 同一次调用在 transcript 里会以 `input_tokens` 和 `inputTokens` 两种形态**嵌套重复出现**，脚本按相邻三元组去重，否则累计值会翻倍；
- 单独计算 `input - cache`，把"便宜部分"和"全价部分"分开，避免被总数误导；
- transcript 路径默认 glob `~/.codebuddy/projects/*/*.jsonl`，取 mtime 最新的一个。

## 五、对开发节奏的结论

1. **知识外置是对的**。`AGENTS.md` + `docs/` + GitHub 已经把关键决策落盘，新会话 5 分钟就能重建上下文——不必再为"记住历史"付出 10 万 token/轮的代价。
2. **一个会话一件事**。本次会话横跨演示模式、棋盘组件、文档、推送、架构文档、用量统计等多个主题，是 input 累计到 7800 万的主因。
3. **长会话不必恐慌，但要主动收尾**。压缩机制保证了不会崩，但每轮 10 万起步的固定成本，意味着"顺手问一句"也不便宜。适合做收尾类小事，不适合再起大改动。
4. **换会话前先 commit**。沙箱随会话消失，仓库不会。`docs/HANDOFF.md` 就是为此写的。
