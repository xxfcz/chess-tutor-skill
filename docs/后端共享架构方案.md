# 棋类教练产品架构对比与单后端复用方案

> 范围：三个同款产品并存时的「是否重复开发」「能否共用底座」问题，以及落地为单一 Node.js 后端的方案。
> 状态：结论已与用户对齐（2026-10-24）。本文为唯一真相文档，历史中间结论（目录为空、Python 无法复用等）已作废。

---

## 1. 三个项目的真实身份

| 项目 | 语言 / 运行时 | 引擎 | 前端 | 许可 | 与你的关系 |
|---|---|---|---|---|---|
| `chess_tutor-stefan` | JS / Next.js（Web） | Stockfish.wasm | React | **GPL-3.0** | 仅设计参考，不可作代码基座 |
| `ai-chess-wx` | JS / 微信原生 | 远端 Stockfish + 本地 JS 引擎 | WXML | 自有 IP | 已落地的主基座 |
| `chess-coach`（即 `chess-tutor-skill`） | 网站起点为 Python/Flask，**可改 Node.js** | 本地 Stockfish 二进制 | HTML/JS | 自有 | WorkBuddy 技能 + 网站，验证「技能方向」 |

- `chess_tutor-stefan`：用户既有选型文档（`ai-chess-wx/docs/黑白格大师_vs_chess_tutor_选型分析.md`）已判定——仅约 7% 纯逻辑可移植、且整体 GPL-3.0 与闭源商业冲突，**只当设计蓝图，不碰代码**。
- `ai-chess-wx`：微信原生小程序「黑白格大师 / 国象 AI 分析」，核心棋类逻辑落在 `utils/`，且**刻意写成无 `wx`/DOM/Canvas 依赖的 L0 纯 Node 模块**，可独立 Node 测试。
- `chess-coach`：`chess-tutor-skill` 目录实际是 `chess-coach` 技能（v2.1.0，四形态：PGN 复盘画像 / 实时对弈陪练 / 观战解说 / 开局学习），所谓「网站」即 `play/`。**用户明确：后端不限定 Python，可改为 Node.js。**

---

## 2. 重复开发之嫌：成立，但有前提

功能上三项目高度重叠（分析 / 教练 / 对弈 / 复盘 / 开局 都覆盖，约 80% 同一款产品）。是否构成「代码重复」取决于后端语言：

- 若网站坚持从 `chess_tutor-stefan` 照搬 → 会重造小程序已有的领域内核，并继承 GPL-3.0。**这条路必须否决。**
- 若网站后端可改为 Node.js → 与小程序同语言，JS 内核可直接共享，重复之嫌解除。

**关键转折来自用户澄清：技能网站后端可改 Node.js。** 这一条让「不同产品线在后端复用」从设想变成可行路径。

---

## 3. 决定性事实：`chess.imex.de5.net` 已经是小程序后端

经 grep 核实：

- `ai-chess-wx/utils/remote-engine.js` 与 `engine-config.js` 的**内置生产端点就是 `https://chess.imex.de5.net`**；
- `POST {endpoint}/v1` 跑的是云端 Stockfish（AGENTS.md 记：Let's Encrypt 证书有效至 2027-01-14，实测返回 200）；
- 小程序另有一路 LLM 点评走 `https://mp-api.app.workbuddy.host`（workbuddy 云 SDK），**尚未**归到自有服务器。

结论：「主要后端功能承载在自有服务器 `chess.imex.de5.net`」不是从零搭建，而是**把已经跑着的端点做实、做全**。风险极低。

---

## 4. 目标架构：两个前端、一个 Node 后端

```
┌─────────────────────────────┐      ┌─────────────────────────────┐
│ 微信小程序 · 黑白格大师        │      │ 技能网站 + WorkBuddy 技能     │
│ remote-engine.js → /v1,/api  │      │ 复用同一后端；发布 Web 链接   │
└──────────────┬──────────────┘      └──────────────┬──────────────┘
               │                                      │
               └──────────────┬───────────────────────┘
                              ▼
        ┌─────────────────────────────────────────────────────────┐
        │  chess.imex.de5.net · 单一 Node.js 后端                    │
        │                                                           │
        │  ┌────────────┐ ┌────────────┐ ┌────────────────────┐    │
        │  │ 引擎服务    │ │ LLM 教练   │ │ 分析·画像·雷达       │    │
        │  │ Stockfish   │ │ llm-       │ │ 移植 scripts/*.py   │    │
        │  │ 进程 /v1    │ │ provider   │ │                     │    │
        │  └────────────┘ └────────────┘ └────────────────────┘    │
        │  ┌──────────────────────────────────────────────────┐   │
        │  │ 开局库数据：12 开局 ideas/traps（移植 openings.py）│   │
        │  └──────────────────────────────────────────────────┘   │
        │  ┌──────────────────────────────────────────────────┐   │
        │  │ chess-core 共享内核（纯 JS，无 wx/DOM）            │   │
        │  │ 小程序 utils/ L0 提取：chess·game·session·         │   │
        │  │ comment-model·coach 纯逻辑                        │   │
        │  └──────────────────────────────────────────────────┘   │
        └─────────────────────────────────────────────────────────┘
```

- **chess-core（共享内核）**：把 `ai-chess-wx/utils/` 中本就无 `wx`/DOM 依赖的 L0 纯 JS（chess / game / session / comment-model / coach 纯逻辑 / pgn-tree / board-model / tools / geometry）抽成独立包。**服务端（跑 Stockfish + LLM）与小程序客户端 `import` 同一份代码**——这是真正消除重复的地方。
- **服务端独有责任**（只在 Node 后端跑，客户端不碰）：Stockfish 引擎进程、`LLM` 调用、Web 前端托管。
- **技能网站**：Node 后端顺带托管 Web 前端（或静态前端调同一 API）；WorkBuddy 技能脚本也 `import` chess-core。

---

## 5. 复用边界（明确划分）

| 类别 | 内容 | 处理方式 |
|---|---|---|
| **共享（同一份）** | chess-core 纯逻辑：chess / game / session / comment-model / coach 纯逻辑 / pgn-tree / board-model / tools / geometry | 抽成包，服务端 + 小程序客户端共用 |
| **服务端独有** | Stockfish 引擎进程、LLM 调用、Web 前端托管 | 仅 Node 后端实现 |
| **不可共用（各自实现）** | 微信 UI 层（WXML/组件）、wx 绑定传输层（cloud / device / navigation / engine-config） | 小程序侧保留适配层，web 侧写等价层 |
| **规范 + 种子数据** | Python 版 `references/prompts.md` 提示词、分级口径、openings.py 的 12 开局 `ideas/traps` | 移植进 Node 后端，作为跨端口径一致的真相源，**不双向分叉** |

> Python 版 `chess-coach` 的定位是**规范与种子数据**，不是运行时代码。把它当成「跨端口径一致」的真相源（教练口吻、分级阈值、开局文案），移植进 Node 后端即可。

---

## 6. 约束与风险

1. **微信域名白名单**：`chess.imex.de5.net` 已满足 HTTPS + 已在使用，小程序无需改白名单。但若以后拆子域 / 子路径（如 `api.chess...` 或 `/coach`），**必须去 mp 后台「request 合法域名」加一遍**，否则开发者工具绿、真机红（已在 `ai-chess-wx/docs/问题排查与修复记录.md` 踩坑）。
2. **`/v1` 契约不可破坏**：小程序依赖该端点，后端 Node 化后须保持兼容。
3. **LLM 教练归己**：现走 `mp-api.app.workbuddy.host`（workbuddy 云 SDK）。要做到「主要后端都归己」，需把 LLM 教练迁到 `chess.imex.de5.net`，用 `llm-provider` 抽象接 openai-compatible（`ai-chess-wx/docs/平台化产品重构方案.md` §11.5 已规划）。

---

## 7. 实施路线（建议顺序）

1. **建 `chess-core` 骨架**：从 `ai-chess-wx/utils/` 抽 L0 纯 JS 成独立包（`exports` 收口，沿用现有 `.workbuddy/tests/` 单测）；小程序先改引用、零功能改动。
2. **起 Node 后端脚手架**：在 `chess.imex.de5.net` 侧（或本地起等价服务先验证）搭建 `/v1` 兼容端点 + `/api/coach` 雏形，先跑通「小程序不动、后端换 Node」的最小闭环。
3. **搬知识资产**：`openings.py` 的 12 开局转 JSON/JS 模块；`prompts.md` 提示词与分级口径对齐进 Node 后端。
