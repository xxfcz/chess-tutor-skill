### 三个开源项目都没做到的（我的机会）

1. **服务端算力**：Iamsdt / edmozley 引擎都在客户端（7MB 首屏、吃用户 CPU）；我有 8 进程引擎池——可做批量 PGN 分析、多用户并发。
2. **场景平台化**：三家都是"模式硬切"（训练/Live、开局/战术/对弈），没有把场景抽象成配置。
3. **AI 介入可控**：edmozley 每步 commentary、Iamsdt 每步卡片，都没有"用户可调时机与频率"。
4. **与 AI Agent 对弈**：三家都没有这条路。

## 三、各开源项目的「可取之处」清单

### 3.1 Iamsdt-chess（Chess King）

**抄：**

- [ ] **内容外置 JSON + 运行时 `normalize*()` 校验归一**——新增课程只丢一个 JSON，不改代码（内容运营最友好）
- [ ] **tutorial 逐步结构**：`actor(player/opponent)` + `san` + `instruction` + `coaching` + `hint` + `arrows` + `focusSquares`——等于一门可执行的课程 DSL
- [ ] **六档分级 + Chess.com 准确率公式** `103.1668·e^(−0.04354·cpLost) − 3.1669`
- [ ] **结构化卡片代替纯文本流**：`my-move-analysis` / `threat-card` / `best-move-card` / `hint-card` / `gm-thought`
- [ ] **ELO 分档话术库**（600~2200+，每档 20+ 条不重复评语）——把"教练感"做进文案层，而非全靠模型
- [ ] **双引擎策略**：自写 minimax+alpha-beta（零依赖、秒开、可离线）兜底 + Stockfish 主力
- [ ] **优雅降级链**：AI 失败→引擎 markdown 兜底；引擎异常→跳过；摘要失败→本地规则摘要（"永不空屏"）
- [ ] **本地持久化双库**：对局 autosave + 训练进度分库

**不抄：**

- ✗ 零后端（我有服务端算力，这是优势，别丢）
- ✗ key 存 localStorage 直连（公开部署必暴露）——应走我的后端代理
- ✗ 两套内容体系并存（`src/data/*.js` 与 `public/*.json` 功能重叠）
- ✗ 测试面窄（仅 lib 层，UI 与编排层无覆盖）

### 3.2 edmozley/chess

**抄：**

- [ ] **职责硬隔离**："Stockfish 是棋脑，Claude 只是翻译"——prompt 里反复强调 NEVER 自己分析局面，只把引擎结论翻译成人话。**这是根治 LLM 幻觉的最有效一条**
- [ ] **"当前局面优先"上下文工程**：用户问题前硬插 `[CURRENT BOARD STATE - this overrides anything from earlier messages]`，并只保留最近 4 条聊天——专治 LLM 拿历史旧建议当答案
- [ ] **客户端引擎 Promise 化封装**：`uciok`/`readyok` 握手、`info`/`bestmove` 解析、MultiPV、cp/mate，带 10s/15s/30s 超时与失败降级
- [ ] **可点击棋谱（Clickable Notation）**：正则把教练回复里的棋着/方格变成可点击 span，点击即在棋盘高亮——把自然语言与棋盘打通
- [ ] **`moveToEnglish()` 大白话翻译 + `generateBoardContext()` 交易分析**：模拟每个吃子判断"亏/等价/安全/危险（无保护）"——引擎之上的规则化战术护栏
- [ ] **解说按评估波动分类**（move / blunder / brilliant / summary）且**走非关键路径**，失败只返回 null 不影响对弈
- [ ] **库全部自托管，不依赖 CDN**（可离线、更私密）

**不抄：**

- ✗ 关掉 SSL 校验、`db/setup.php` 建表后暴露、无 CSRF、无真正认证
- ✗ 引擎全在客户端（首开大、多用户不在设计目标内）
- ✗ 无测试无 CI

### 3.3 chess_tutor-stefan

**抄（借鉴思路，不碰代码——GPL-3.0）：**

- [ ] **`tacticDetection` 漏着诊断**：每步比对引擎最佳着，判断漏掉了什么（安全吃子含反吃分析、牵制、击双、串击、闪将、悬子）——这是三者里唯一做了**棋类算法层诊断**的，深度比"仅威胁检测"高一个量级
- [ ] **9 种人格系统**（开局教授、醉酒俄派 GM、甘道夫…）——拟人化是 L3 层差异化的有效手段
- [ ] **7 语言类型安全翻译**（`translations.ts` 1907 行）
- [ ] **工程化标准**：jest 233 用例 + 7 Playwright e2e；Docker + nginx + Capacitor 双端
- [ ] **引擎工厂按环境分叉**（Web WASM / 移动 RemoteEngine）——思路可借鉴于我的"远端为主、端上兜底"

**不抄：**

- ✗ GPL-3.0 授权，与闭源商业化冲突
- ✗ 内容打包进 bundle（8.6MB JSON）——应学 Iamsdt 外置化
- ✗ 巨型组件（ChessGame 1031 行 / Tutor 1112 行）

## 四、八问重答

### Q1 小程序 + H5 共用 L0 基座是否可行？先做哪个？

**可行，且应做。** 小程序与 H5 同为 JS/TS 生态，L0（棋局/规则/走子/PGN/点评模型/分析整形）可完全共用；Python 侧（`chess-coach`）代码不共用，只作**规范与内容源**。

两个起点各有优劣：

| 起点 | 优势 | 劣势 |
|---|---|---|
| `ai-chess/src/chess/game.ts` | TypeScript、已有 `game.test.ts`、用 chess.js、结构干净 | 只覆盖规则/FEN/终局，领域逻辑薄 |
| `ai-chess-wx/utils/` | 领域逻辑完整（engine/game/session/comment-model/coach/pgn-tree/board-model/tools/geometry）+ 19 篇文档 | CommonJS、带 wx 适配残留 |

**建议**：以 `ai-chess` 的 `src/chess` 为**骨架（TS）**，吸收小程序 `utils/` 的领域逻辑（TS 重写），L0 用 TS 编写。小程序侧消费**编译产物**（tsc → JS），因小程序无法直接 require TS 源码。

**先做哪个 → 先做 L0 本身，在 `ai-chess`（H5）仓库里长大。**

理由：
1. H5 无 2MB 包体限制、无域名白名单、无 wx 适配成本，是**摩擦最低**的试验场；
2. L0 在 H5 跑通并补齐测试后，小程序直接消费，避免小程序反复改；
3. 小程序适合做"消费端"而非"试验场"。

⚠️ 需先给 `ai-chess` **重新定位**：其 `AGENTS.md` 现写明"纯前端截图识别 MVP、不实现小程序"。这与目标（多场景教学平台）有差距，需先改定位再动工。

### Q2 如何充分利用 `chess.imex.de5.net`？

探针实测：`status ok`、Stockfish 15.1、**8 进程引擎池（idle 8/8）**、uptime 11 天——是带并发能力的真服务，不是玩具端点。

这是我对三个开源项目的**最大结构性优势**（它们引擎都在客户端）。建议扩展为：

| 能力 | 说明 |
|---|---|
| `/v1` 引擎分析 | **保持现有契约不变**（小程序依赖） |
| `/api/openings` | 托管开局/教程 JSON（Q3），两端拉取，**内容热更新不发包** |
| `/api/coach` | LLM 代理（`llm-provider` 抽象），**把 key 从客户端收归服务端**——正面解决 Iamsdt 的 key 暴露问题 |
| `/api/analyze`（批量） | 整局 PGN 逐着分析、画像计算，长任务后端跑，前端不卡 |
| `/healthz` | 已有，可作为两端的能力探测端点 |

8 并发意味着可支撑批量分析与多用户。注意：新增子域/子路径需去 mp 后台加「request 合法域名」。

### Q3 内置开局主要走法 + 预置点评（JSON 提供），如何？

**强烈支持，这是降本增效最优解。** 正是 Iamsdt 的核心优势（"内容即数据"），也是 doc04 公认的"内容运营最友好"。

已有资产可直接转化：`scripts/openings.py`（12 条，含 `ideas`/`traps` 中文文案）+ `step_notes.py`（逐手文案）。

建议 schema（融合 Iamsdt tutorial 与我的 step_notes）：

```json
{
  "id": "italian", "name": "意大利开局", "eco": "C50",
  "moves": [ { "actor": "player", "san": "e4", "uci": "e2e4" } ],
  "notes": [ { "moveIdx": 0, "instruction": "...", "coaching": "...",
               "hint": "...", "arrows": ["e2e4"], "focusSquares": ["e4"] } ],
  "traps": [ { "afterMove": 3, "desc": "..." } ]
}
```

**收益**：开局前 8–10 手高度确定，预置点评覆盖率可达 90%+，LLM 只在"用户偏离谱"或"主动提问"时介入——直接回答 Q6 的"太浪费"。

**落点**：JSON 由后端托管（Q2），两端拉取；运行时做 `normalize` 校验防手写 JSON 出错。

⚠️ 规模差距：Iamsdt 54 条识别/48 教程，stefan 12,379 条 ECO。建议**先做 12–20 条精编中文教程**（质量 > 数量），比堆量实际。

### Q4 对手类型：Stockfish / 第三方 LLM / AI Agent，怎么设计？

三者**必须分层定义**，否则 LLM 会走出幻觉着法：

| 类型 | 正确姿势 | 错误姿势 |
|---|---|---|
| **Stockfish** | 默认对手，`skill level`/`movetime`/`depth` 调棋力 | — |
| **第三方 LLM** | LLM 只做**风格/人格**（参考 stefan 9 人格）或在引擎 Top-N 里**挑选**；着法仍由引擎产出 | ❌ 让 LLM 自己想棋（必幻觉） |
| **AI Agent** | 见 Q7 | ❌ 让 Agent 自由输出 SAN |

**统一抽象**：

```ts
interface OpponentProvider {
  getMove(fen: string, ctx: GameCtx): Promise<{ move: string; meta?: unknown }>
}
```

三种实现对上层同构，这也正是 Q5 平台化的价值所在。

> 关键设计：LLM/Agent 对手**一律走"引擎给候选、模型只挑"**——这正是 `ai-chess-wx` 的 `===DEMO===` 协议（系统生成合法序列，模型只回 `cand:"#1"`）的思路。防幻觉 + 棋力有下限 + 保留"人味"，三者兼得。

### Q5 抽象成基础业务平台（场景 = 配置），这个思路如何？

**非常认同，且是三个开源项目都没做到的**（它们都是模式硬切）。你的四要素抽象（棋局/走子/点评/教学）抓得准。

建议元模型：

- **Session（棋局）**：FEN / PGN / 走子历史 / 分支树
- **Actor（走子方）**：human / engine / llm / agent（即 Q4 的 `OpponentProvider`）
- **Intervention（点评介入）**：时机 + 频率 + 形式（即 Q6）
- **Content（教学内容）**：开局 / 题库 / 教程 JSON（即 Q3）
- **Scene（场景）= 上述四者的配置组合**

| 场景 | Session | Actor | Intervention | Content |
|---|---|---|---|---|
| 对弈 | 实时 | human vs engine | `on-mistake` | — |
| 开局练习 | 剧本化 | 教程脚本驱动 | 逐步校验 | 教程 JSON |
| 打谱 | 只读导航 | 无 | `on-request` | PGN |

**风险提醒**：别自顶向下设计成"配置地狱"。建议先做 3 个真实场景反推抽象。

> 附带收益：这正好从结构上**规避了 Iamsdt / stefan 的"巨型编排组件"技术债**——场景是配置，不是硬编码在 `App.jsx` 里的分支。

### Q6 AI 每步大白话太浪费，改为可配时机与频率？AI 作用还能怎么发散？

同意。edmozley 就是每步 commentary，Iamsdt 每步卡片，都浪费。

**介入时机（用户可配）**：

| 档位 | 触发 |
|---|---|
| `off` | 不介入 |
| `on-mistake` | 仅分级 ≥ Mistake/Blunder（最省） |
| `on-request` | 仅用户点"讲讲这步"或提问 |
| `on-branch` | 仅关键分歧点 / 出谱时 |
| `every-n` | 每 N 步 |
| `summary` | 仅终局总结 |

**AI 作用发散（不止讲解）**：

- 着法讲解（事后）
- **提示危险（事前预警）**——edmozley 的交易分析："这步吃了会被反吃"
- **回答问题**（自由问答，用"当前局面优先"上下文工程防旧答案）
- 出招建议 hint（Iamsdt `hint-card`）
- **复盘总结 + 训练处方**（市场分析的 L2 个性化层）
- **错题访谈**：追问思考过程，区分"计算错 / 知识盲区 / 习惯问题"

**成本护栏**：预置点评（Q3）覆盖常规步 → LLM 只处理"预置库未命中"的步。

### Q7 与现有 AI Agent（如 WorkBuddy）对弈，是创意吗？

**是真创意且可行**，但要把"不消耗额外 token"这点说准：

> 严格说，Agent 下棋**会消耗**你的 WorkBuddy 会话额度（每日赠送积分），并非零成本；真正的优势是**不需要另配 LLM Provider、不另付 API 费用**。宣传口径不要建立在"零消耗"上。

**真实价值**：① 零配置（免 key）；② 天然拟人、有性格；③ 可边下边聊（解说 / 教学 / 互动）——纯引擎做不到；④ "跟 AI Agent 下棋"本身是传播卖点。

**落地分三阶段**（参考《方案初探》的三种接法）：

1. **阶段一·零集成（聊天式）**：贴 FEN 给 Agent，Agent 回一步，手动落子。**零开发**，先验证棋力与体验是否可接受。
2. **阶段二·HTTP 对接（推荐）**：后端暴露 `GET /api/agent/state` + `POST /api/agent/move`；WorkBuddy 侧实现 `OpponentProvider.getMove(fen)`，前端每步 POST。
   - 接口约定要定死：传 FEN 还是 move 序列？返回 SAN 还是 UCI？有无鉴权？
3. **阶段三·MCP（可选）**：只有想让 Agent"自主驱盘"或接入多工具链时才做；单纯人机对弈不需要。

**重要建议**：Agent 对手也走"引擎给候选、Agent 挑选 + 解说"（同 Q4）。这样防幻觉、棋力有下限、保留人味，且与 LLM 对手复用同一套机制。

### Q8 Iamsdt 值得借鉴吗？单文件过大怎么看？

**值得，但要挑着抄。** 见 §3.1 清单。核心是"内容即数据 + 结构化卡片 + 分级口径 + 优雅降级"，而非它的零后端架构。

**单文件过大**：doc02 自列 `training-panel.jsx` 83KB / `chat-panel.jsx` 45KB / `App.jsx` 41KB；doc04 指出这是**通病**（stefan `ChessGame` 1031 行 / `Tutor` 1112 行）——"棋盘 + 对话 + 分析"三栏应用天然把编排逻辑堆进单文件。

**对你的启示**：这正是 Q5 平台化的反例。若场景做成配置而非硬编码进巨型编排组件，可从结构上避免此债。对策：

- 编排层只做"场景配置 → 组装 Scene 对象"
- 交互逻辑下沉到 hook / lib
- 巨型面板按**能力**而非**页面**拆（如 `chat-panel` → message-list / card-renderer / input-bar）
